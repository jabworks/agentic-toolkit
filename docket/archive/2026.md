## 16. Supply-chain lint does not cover plugin-level files (2026-08-11) — ✅ DONE 2026-08-12

`scripts/check-supply-chain.mjs` walked `skills/` only, so the repo's first plugin-level executable (`plugins/condux/install.mjs`, shipped by #9) and the `INSTALL.md` instructing an agent to run it were scanned by nothing — all four of the rules that exist for exactly that shape were reachable in a tree the checker never opened.

#18 predicted this would be #11-shaped work because "the allow-list keys and its inventory both assume `skills/`". It was not. Both are keyed to repo-relative source paths already, so they took a `plugins/` prefix unchanged and the script inventory needed no edit at all. The real coupling was one constant doing two jobs: `SCAN_ROOT` named both the tree to walk and the tree to resolve `references/…` citations against. Those are different questions — skills are the only tree that ships `references/` helpers, and plugin-level prose cites them by the same relative shape (concord's plugin README says `references/INSTALL.md`, meaning `skills/remember/references/INSTALL.md`). Split into `SCAN_ROOTS` and `SIBLING_ROOT`; a probe that widened the scan without splitting them reported that live link as dangling, which is how the trap was found before it shipped rather than after.

Allow-list written against real findings, not guesses: 11 findings across 4 codes over the 14 new files, closed by 2 entries. `plugins/condux/install.mjs` (SCRIPT-FILE) also clears the 8 INVOKES-SCRIPT findings on the `node … install.mjs` lines in `INSTALL.md` and `README.md`, since invocations match by basename — the coupling is recorded in the entry's reason so a later reader does not delete one and silently lose the other. `www.npmjs.com` (EXTERNAL-DOMAIN) is the `@jabworks/condux` package page cited in prose; nothing fetches it.

The entry's open question is answered: docket's installer machinery is seen **once**, at `skills/record/server/`. `plugins/docket/` and `plugins/concord/` are README-only, and the plugin-root copy lives in `dist/`, which this checker deliberately does not walk. 175 files = 161 skills + 14 plugins, no overlap. That `dist/` exclusion is unchanged and still correct — byte-parity is guarded by `dist-mirror.test.mjs` and keying the allow-list to source paths keeps one reason per fact.

Code review raised one Important finding, fixed in branch: `collectFiles`' second parameter changed from a single root string to an array, and it is exported. A stale string caller would iterate the string character by character, match no directory, and hand back an empty list — the checker would then report clean over zero files, which is the one failure a security gate cannot afford and which this file's own test comment already names ("a checker that silently scans nothing passes forever"). A string is now normalised to a single-element array, with a test that fails without it. Left as noted, not fixed: declaring `plugins/condux/install.mjs` whitelists the *basename* `install.mjs` for INVOKES-SCRIPT everywhere, since invocations match by basename. The blind spot is narrow — an actual new `install.mjs` file still trips SCRIPT-FILE, which is keyed to the full path, so only prose naming an `install.mjs` this repo does not ship gets through — and `doctor.mjs` and `install.sh` set the precedent already.

Verification: `node --test` 235 → 238, checker clean over 175 files (was 159 at #13, plus 2 from #18). All three new tests triggered to fail by mutation, not assertion: narrowing `SCAN_ROOTS` back to `['skills']` fails 2 (the plugins-coverage anchor, and the live assertion — because the 2 allow-list entries go unused, which the reasonless-AND-unused rule from #13 catches on its own), and resolving citations against the citing file's own tree fails 3 (both citation regressions plus the live assertion). The coverage test anchors on the executable *and* the prose that runs it, because the existing skills-tree assertion passes at full strength on a scan that opens neither. No version bump — `scripts/` and `tests/` only, no skill or plugin file touched, same call as #15.

## 18. Warn about conflicting skill libraries at install and doctor time (2026-08-11) — ✅ DONE 2026-08-11

Verification: shipped in condux 2.13.0. Registry is data (skills/condux-doctor/conflicts.json) read by both callers through a shared conflicts.mjs, so the table naming another project skills exists once — a test fails if either script names a conflicting library in code. Report grammar gained a fifth status, warn: a competing library is not broken (condux installed correctly, and the installer verify beat keys its exit code on broken) and done would be a lie. Two detection surfaces, because a machine can carry the overlap either way: host plugin registrations (installed_plugins.json keys, config.toml [plugins."name@marketplace"] headers) and the four loose skills directories, with a floor of 2 matching names so a lone brainstorming/ accuses nobody. Registrations are read rather than plugins/cache/, which outlives the install that created it.

node --test 223 → 235 (12 new). Each triggered to fail before passing, by mutation rather than assertion: warn→broken failed 3, floor→1 failed the false-positive guard, dropping the doctor row failed the report check, hardcoding the name failed the single-source check, removing the resolve check failed the dangling-symlink case, and adding one of our own skill names to the registry failed the self-collision guard. That last guard came out of code review: the detector matches directory names, so a registry name equal to a skill we ship would accuse every clean condux install of conflicting with itself. There is no overlap today because 2.0.0 renamed condux off superpowers vocabulary on purpose; the test is what keeps that true.

That last test exists because running it live found a false positive the design had not anticipated. The first detector read ~/.claude/skills with readdirSync and counted names, and on this machine reported 14 superpowers skills present. All 14 were symlinks into a ~/.agents/skills tree that had since been pruned — dead links a host cannot load. Detection now follows the link (existsSync is false for a dangling one) and reports the resolved parent directory rather than the one holding the link, since that is where removing anything would have an effect. The corrected run reports the plugin surface alone, which is the truth here, and still exits 0. conflicts.mjs is allow-listed in the supply-chain scanner with its narrowness as the reason: filesystem reads and name matching, no network, no child process, asserted by test.

Not done here: Plannotator (plan-review lineage) is documented in the README but not in the registry — no detection surface for it was verified, and a wrong name in a shipped warning is worse than no warning. The removal half across all three plugins remains #2.

## 13. Generalize supply-chain lint across all skills, not one template (2026-08-09) — ✅ DONE 2026-08-09

We already do one of these checks — for exactly one file. `skill-invariants.test.mjs:105`
("plan-review HTML template makes no external network references") greps that
single template for `//` URLs. That is the `EXTERNAL-DOMAIN` rule, hand-scoped
to one artifact because that artifact was a known risk. Nothing generalizes it,
and no other rule in the family exists at all.

Adjacent but different: `script-safety.test.mjs` tests the *runtime* behaviour
of three specific installer scripts (path escape, idempotency, refusing to
overwrite malformed config) and `browser-security.test.mjs` tests plan-review's
HTML escaping. Both check that our known scripts behave; neither reads a
SKILL.md to see what it instructs an agent to fetch or execute. That is the
gap — and we publish to a public marketplace across three channels.

Upstream runs `npx @microsoft/vally-cli lint ./skills` nightly
(`.github/workflows/skill-quality-report.yml`) and gates PRs with
`skill-check.yml`. Vally's lint (MIT, read from the 0.13.0 tarball —
`dist/skill/reference-scanner.js` + `external-dep-checker.js`) is purely
supply-chain, driven by two allow-list files (`knownDomainsFile`,
`allowedExternalDepsFile`):

| code | flags |
|---|---|
| `EXTERNAL-DOMAIN` | URL to a domain not on the known list |
| `HTTP-NOT-HTTPS` | plaintext HTTP reference |
| `PIPE-TO-SHELL` | `curl ... \| sh` shaped instructions |
| `INVOKES-SCRIPT` | skill body tells the agent to run a script |
| `SCRIPT-FILE` | bundled executable script |
| `SCRIPT-NO-SRI` | remote script without subresource integrity |
| `NON-BUILTIN-TOOL-REF` | references a tool outside the host's builtins |
| `FILE-READ-ERROR` | referenced file unreadable |

Several of ours trip these on purpose — docket ships `install.sh` and
`server/mcp-server.mjs` behind `.mcp.json`, condux ships `session-start.mjs` as
a SessionStart hook. That is the argument *for* an allow-list rather than
against the check: the value is that a *new* unreviewed one shows up in CI.

Adoption shape, per the no-plugin-dependencies ladder: do **not** take the CLI
dependency. Port the eight rule codes into a dependency-free
`tests/skill-supply-chain.test.mjs` with a checked-in allow-list, written the
way `frontmatter-canonical.test.mjs` is — no devDependency, same module usable
from the pre-commit hook. (`@microsoft/vally-cli` would be a repo dev
dependency, not a shipped-plugin one, so it is defensible; it is just more than
this needs.)

Cheapest of the awesome-copilot findings to land. The plan-review no-egress test
is the proof it works and the thing to subsume: once the general check exists
with plan-review's template on the allow-list, that bespoke test can retire.

Found 2026-08-09 surveying awesome-copilot's maintenance machinery.

Verification: shipped as PR #41 (squash 0296f73). scripts/check-supply-chain.mjs ports 7 of 8 vally rule codes dependency-free; NON-BUILTIN-TOOL-REF deliberately omitted (no canonical host-builtin list) and SCRIPT-NO-SRI renamed UNPINNED-REMOTE-REF, both recorded in the file header. ## 15. Three cheap skill-validation checks we do not have (2026-08-09) — ✅ DONE 2026-08-10

Small additions to `tests/skill-invariants.test.mjs`, each a few lines, all
lifted from `eng/validate-skills.mjs` + `eng/constants.mjs` in
`github/awesome-copilot` (MIT). Batch them into one pass.

- **Description floor.** We enforce ceilings (description <= 500, frontmatter
  total <= 1024) and no floor. Upstream uses
  `SKILL_DESCRIPTION_MIN_LENGTH = 10`. A one-word description passes every check
  we have today while being useless for routing — and routing quality is the
  thing we measure hardest.
- **Bundled asset size cap.** Upstream refuses any bundled asset over 5 MB. We
  check no sizes at all, and docket ships a whole `server/` tree that the
  marketplace has to carry.
- **Asset directory allow-list.** Upstream only walks `references/`, `assets/`,
  `scripts/` inside a skill. Our `references/` convention is documented in
  `toolkit-skill-standards` but unenforced, so a stray directory ships silently
  through the mirror.

Not worth a workflow on their own; good filler alongside #13, which touches the
same test surface.

Found 2026-08-09 surveying awesome-copilot's maintenance machinery.
