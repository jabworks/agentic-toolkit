## 2 + 17. UNINSTALL.md — the removal half of the ease-of-install convention, and condux's --uninstall gap (2026-08-05 / 2026-08-11) — ✅ DONE 2026-08-12

Closed together, as the entries insisted. #2 was the documented procedure and #17 the machinery underneath it, and the question they shared — what a plugin may do about host state it sets but does not own — is policy that no amount of machinery answers.

**Ruling: an uninstaller reverses only what it exclusively owns.** `[features] hooks = true` has three writers (condux's front door, concord's hook installer, plan-review's hook installer) and no owner, so nobody clears it. This promotes behaviour that already existed into a stated rule: condux's source already carried the comment, but nothing a *user* read said so, which makes a correct outcome look like an incomplete removal. Every front door now names the other riders, and the Codex row reports `warn` rather than `done` so the residue is visible instead of silent. Reference-counting was rejected — it needs each plugin to carry a map of its siblings' registration shapes, the cross-plugin knowledge the no-plugin-deps rule bans, and it fails in the dangerous direction when a probe is wrong. Prompting the user was rejected as moving a decision onto someone with less information than we have.

**Machinery lives in the writer, not the front door.** The deciding evidence was concord's existing `--uninstall`: not a separate routine but a `MODE` flag inside the same script, reusing its own detect and report. Reversal is cheap there because the writer already knows the shape of what it wrote. So plan-review's hook installer, docket's `install.sh`, and the Codex agents installer each gained the same mode, and condux's front door delegates to them — symmetric with install, which already delegated. Reversing from the front door instead would have meant re-deriving the agent TOML names and the Stop hook's entry shape, and scattered install knowledge is exactly what made condux's install story wrong until #9.

Two corrections found by integration review rather than by test. docket's uninstall wrote a temp file and `mv`'d it over `config.toml`, silently widening 0600 to the caller's umask on a file that holds Codex credentials; it now rewrites through the existing inode so the user's mode survives, asserted. And its verify beat still reported "server answers initialize", which is true after an uninstall and proves nothing — it now confirms no registration remains and fails if one does. A third came from the agent doing better than its brief: agent names are derived from `.md` frontmatter rather than filenames, so a rename cannot desync install from uninstall.

`.bak` is never restored, verified rather than assumed: `install.sh:47` rewrites the backup at the start of every run, so after a second install it holds an already-registered config and restoring it would reinstate the very registration being removed. Removal is surgical.

Verification: `node --test` 240 → 241, supply chain clean over 180 files, sync clean. Round-trips per installer in sandboxes, 18 assertions total: shared flag survives every path, sibling registrations survive (concord's `SessionStart`, an unrelated `Stop` entry, `[mcp_servers.other]`, opencode's `theme`, a hand-placed agent TOML), `config.toml` stays 0600, `--dry-run` writes nothing (whole-sandbox hash before and after), second runs exit 0.

The guard work found a hole in itself, which is the part worth remembering. Widening #19's front-door test to `UNINSTALL.md` looked sufficient and was not: the rule only fires when a document of that kind exists *somewhere* in the tree, and no plugin has a buried `UNINSTALL.md` — concord's removal steps live inside its deep `INSTALL.md`, docket's did not exist at all. So deleting all three front doors passed. Placement was guarded, existence was not. A separate test now keys the obligation off the install front door: a plugin that tells a user how to register something owes them the reverse. Found by mutation, which is why mutation-testing every new guard is the standing rule and not a formality.

One test edited with sign-off rather than silently: `tests/script-safety.test.mjs:220` asserted the old copy `/shared with other plugins/`. The three behavioural assertions in that test were already passing; only the phrasing had changed. It now asserts the report names the actual riders, which is strictly stronger and matches the ruling.

Versions split three ways rather than moving together, through toolkit-change-control: condux 2.13.0 → 2.14.0 and docket 0.3.2 → 0.4.0 (skill edit, new capability — uninstall genuinely works where it did not), concord 0.4.1 → 0.4.2 (its installer already had `--uninstall`; this ships the document only, so doc-inside-a-plugin → patch, the same call #19 took).

Design and spec: the design was working state and is gone (docket #34); `specs/uninstall-convention/` and PR #51 are the surviving record.

## 19. INSTALL.md is buried for docket and concord, at the plugin root only for condux (2026-08-11) — ✅ DONE 2026-08-12

**Wrap**, following #9's precedent for condux. The entry named a check to run before choosing, and running it decided the item: *does anything resolve paths relative to the INSTALL.md's own location?* Both deep documents do, in their first step — `skills/remember/references/INSTALL.md:18` defines `SKILL` as "this file's parent's parent", and `skills/record/server/INSTALL.md:19` defines `SERVER` as an absolute path to `mcp-server.mjs` "in this directory". So **Move** is out: relocating either silently breaks its own step 0, on top of #9's standing argument that `plugins/` never reaches the `npx skills add` tree. Contrast condux's plugin-level document, which is stable precisely because it anchors on `$PLUGIN_ROOT` and sits at that root.

**Generate** is weaker than it looks, and this is worth recording because #12 will make the same argument look attractive again. A generated *copy* inherits the broken document-relative base — that is the same defect as Move, arrived at by a build step. A generated *pointer* cannot derive the per-plugin host table, which is the only content a user actually needs at the root: concord registers on Codex alone and reports `skipped` twice; docket skips Claude Code because the plugin's own `.mcp.json` covers it. Generation would produce a stub that says less than the wrap it replaced. Generate-over-test is right when the target is derivable; here it is not.

Two front doors written, each carrying the host table, the one-command path, the doctor invocation, and a source-layout note saying which copy to edit. concord's also records *why* it is a pointer rather than a copy, since that is the trap the next person will walk into. No new sync machinery: `sync_plugin_files` already copies every regular file in `plugins/<name>/` and `plugin-files.test.mjs` guards each byte-for-byte.

Two tests, both generalised past the two plugins that prompted them. `a plugin whose install procedure is buried also has one at its root` walks the shipped tree for any `INSTALL.md` and fails when none sits at the plugin root — so a future plugin that buries its procedure is caught without anyone remembering this item. `every path a plugin-level INSTALL.md cites resolves in its dist tree` is the honesty half of the wrap: the front door's whole job is naming where the real procedure lives, so a stale path in it is worse than no front door. It resolves against the dist plugin root (what a user lands on) and the repo root (so "edit the source, never the mirror" notes are not read as dangling), skipping placeholders and host-machine paths.

| code | flags |
|---|---|
| `EXTERNAL-DOMAIN` | URL to a domain not on the known list |
| `HTTP-NOT-HTTPS` | plaintext HTTP reference |
| `PIPE-TO-SHELL` | `curl ... \| sh` shaped instructions |
| `INVOKES-SCRIPT` | skill body tells the agent to run a script |
| `SCRIPT-FILE` | bundled executable script |
| `SCRIPT-NO-SRI` | remote script without subresource integrity |
| `NON-BUILTIN-TOOL-REF` | references a tool outside the host's builtins |
| `FILE-READ-ERROR` | referenced file unreadable |

`server/mcp-server.mjs` behind `.mcp.json`, condux ships `session-start.mjs` as

this needs.)

Cheapest of the awesome-copilot findings to land. The plan-review no-egress test

## 49. annotate-server directory-mode test races the feedback file write (2026-08-22) — ✅ DONE 2026-08-23

`tests/annotate-server.test.mjs:54` — "annotate-server directory mode: doc manifest, per-doc content, grouped feedback" fails intermittently:

```
AssertionError: The input did not match /\*\*Decision:\*\* Request Revisions/. Input: ''
```

**Not flakiness — a real race, and the empty string is the tell.** The file existed and was empty, so this is not a missing write or a timeout.

`annotate-server.js:265` writes with `fs.writeFileSync(feedbackFile, md)`, which is `open(O_WRONLY|O_CREAT|O_TRUNC)` followed by `write()` — two syscalls, in a different process. The test waits on **existence** and then reads once:

```js
const deadline = Date.now() + 2000;
while (!fs.existsSync(feedbackFile) && Date.now() < deadline) {
  await new Promise((r) => setTimeout(r, 50));
}
const feedback = fs.readFileSync(feedbackFile, 'utf8');
```

A read landing between the server's `open` and its `write` sees a created, truncated, still-empty file. `existsSync` is satisfied the instant `O_CREAT` lands, so the loop exits early and the single read returns `''`.

**Reproduction conditions:** observed 3 failures in ~12 full-suite runs on 2026-08-22, every one while local preview servers (`python3 -m http.server`) and Chrome were competing for CPU; zero failures in nine runs on an otherwise idle machine, and 3/3 passes when run in isolation. CPU contention widens the open→write window, which is why it looks load-correlated.

**Fix — wait for content, not for existence:**

```js
let feedback = '';
const deadline = Date.now() + 2000;
while (Date.now() < deadline) {
  try { feedback = fs.readFileSync(feedbackFile, 'utf8'); } catch {}
  if (feedback.includes('**Decision:**')) break;
  await new Promise((r) => setTimeout(r, 50));
}
```

The `try/catch` also removes the second latent bug in the current code: if the deadline expires before the file is created at all, `readFileSync` throws `ENOENT` and the test fails with a stack trace instead of a useful assertion message.

Worth checking whether the single-file mode test (`annotate-server.js:279`, same `writeFileSync` shape) has the same wait pattern.

An alternative worth weighing: have the server write to a temp file and `rename()` it into place, which is atomic on POSIX and fixes it for every consumer rather than just the test. That is the better fix if anything other than this test ever polls the feedback file — `/discovery` and `/draft-plan` both long-poll `/api/decision` rather than reading the file, so today the test is the only reader.

Verification: Both fixes shipped, because they close the race at different layers and the entry's own follow-up question turned out to matter. **Server side** — `annotate-server.js` gained `writeFileAtomic` (sibling temp + `renameSync`, falling back to a direct write if rename throws), and *both* `feedbackFile` writes now use it: steer mode and manual mode. The single-file mode check the entry asked for came back yes — `tests/annotate-server.test.mjs` had the identical wait-on-existence pattern at the manual-mode site, so it carried the same latent bug and was fixed too. The alternative the entry weighed was taken rather than the test-only fix: today the test is the only reader, but atomic-rename means a future reader cannot reintroduce this. **Test side** — a shared `readWhenReady(file, marker)` helper polls for *content*, and its `try/catch` turns an expired deadline into a failed match instead of an ENOENT stack trace.

The race was reproduced before it was fixed, which corrected the method on the way: a first harness "reproduced" nothing because the widened open→write window was a busy-wait in the same process, so the reader never got the event loop — single-threaded JS made the simulation vacuous. Re-run with the writer as a genuine child process (as the server is), the matrix is unambiguous: old writer + old reader reads `""` — the exact `Input: ''` symptom filed here — while old+new, new+old and new+new all read the complete file. ## 55. Merge a duplicate case's `accept` in the trigger corpus, or stop dropping it silently (2026-08-25) — ✅ DONE 2026-08-26

Found while shipping #53 (A3c). `scripts/eval-triggers.mjs` dedups the corpus on
`query + "||" + expected`. #53 made a duplicate's `disallowed` merge into the kept
case; its `accept` is still dropped, silently.

Why #53 did not just fix both: `accept` feeds `isHit`. Widening a kept case's
accept set can flip a MISS to a HIT and move A3's ~89-92% operating band — the
number the whole health campaign is judged on, and the exact thing #53's
separate-metric decision existed to protect. Doing it inside #53 would have moved
the band silently, inside a change whose premise was band comparability.

Measured 2026-08-25: 19 duplicate keys in the corpus, **2 with divergent accept**:

| query | kept | dropped |
|---|---|---|
| `is it safe to hand-edit dist to hotfix this` | toolkit-change-control, accept `["toolkit-failure-archaeology"]` | toolkit-debugging-playbook, accept `[]` |
| `is argument-hint a real frontmatter field` | toolkit-plugin-reference, accept `["toolkit-skill-standards"]` | toolkit-skill-standards, accept `[]` |

In both, the wider set is the one kept — `readdirSync` returns the owning skill's
directory first, alphabetically, by accident. So the drop is **inert today** and
merging would be a no-op on the band. That is luck, not a property: renaming a
skill, or adding a third file carrying the same query with a wider accept, flips
it without warning.

Two defensible fixes, decide when picked up:
1. Merge `accept` like `disallowed`, and re-run a band to confirm the no-op
   empirically rather than by inspection (~10 min, one trial).
2. Make the drop loud instead — fail `tests/trigger-eval-corpus.test.mjs` when two
   cases share a dedup key with divergent `accept`, forcing the corpus to agree
   with itself. Cheaper, no band risk, and arguably the real defect: the same query
   asserting two different things in two files is a corpus bug either way.

Leaning (2) — the current entry in A3c documents the drop as known and inert, and
option 2 keeps that true without ever touching isHit.

## 60. Pass two: technical-spec's templates read heavy (2026-08-26) — ✅ DONE 2026-08-26

Pain point 4 of the five reported against discovery's design output on

The symptom: the spec a session produces is a hard read afterwards.
`decisions.md`'s template is four prose headings per decision — Context,

twenty-four headings of prose with no scannable layer. `implementation.md`

shape with a density budget, tables where a table is honest, and prose
reserved for the reasoning that cannot be tabulated. What pass one learned is
that "be concise" is advice, and advice is what produced the walls — the
budget has to be a number.

**Known cost, accepted when this was deferred:** the design-doc to
`decisions.md` mapping gets designed twice, once as pass one's section-card
contract and once here. Read `skills/discovery/SKILL.md`'s "The Section Card"
before starting — the §-card shape is the input this template consumes, and
the two should agree rather than each invent a structure.
