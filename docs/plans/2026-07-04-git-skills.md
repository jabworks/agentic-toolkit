# Plan: git-commit + git-operations skills

> Date: 2026-07-04

## Overview

**Goal:** Ship two sibling toolkit skills — `git-commit` (craft a conventional-commit message and run the commit safely) and `git-operations` (a decision router: situation → which git operation → safe execution + undo path) — with `git-operations` cross-linking into `git-commit`.

**Approach:** Build `git-commit` first so the router's cross-link resolves on day one. Each skill is authored under `skills/<name>/` (SKILL.md + `references/`), then packaged per the `plugin-foundry` checklist (Codex + Claude manifests, marketplace registration, dist mirror via `scripts/sync.sh`). Content tasks are separated from packaging tasks so each is a standalone-reviewable unit.

**Tech / conventions:** Markdown skills only — no code, no runtime deps. Commands shown generic with an "⚙ Adjust these" callout carrying Harvey's defaults (`rtk`-prefixed git, `-s` signoff). `dist/` is a verbatim mirror of `skills/` produced by `scripts/sync.sh` — never hand-edited.

## Global Constraints

- SKILL.md `description`: triggering conditions only, starts with "Use when…", ≤ 500 chars; frontmatter total ≤ 1024 chars.
- **Prefer modern git porcelain over legacy `checkout`** across both skills: `git switch <branch>` / `git switch -c <new>` for branch moves/creation, `git restore <path>` / `git restore --staged <path>` for discarding/unstaging. Reserve `git checkout` only for cases with no modern equivalent (and call those out explicitly). Never route a branch or file operation through `checkout` when `switch`/`restore` covers it.
- `skills` path in every `plugin.json` must start with `./` (`"./skills/<name>"`).
- New standalone plugin `plugin.json` `version` starts at `1.0.0` (no toolkit-wide version field in marketplace.json).
- `dist/plugins/<name>/skills/<name>/` must be a verbatim mirror of `skills/<name>/` — sync with `bash scripts/sync.sh <name>`, never edit `dist/` by hand.
- No plugin dependencies — skills must not assume any MCP/plugin (e.g. context-mode) is installed.
- Commit style: `feat:` prefix, `-s` signoff, no `Co-Authored-By` trailer.
- Marketplace entries in this repo use the lean shape actually present: `name`, `description`, `author.name`, `source`, `category` — not the fuller shape in the foundry doc.

## Task 1: Author `git-commit` content

**What:** Write `skills/git-commit/SKILL.md` and `skills/git-commit/references/commit-types.md`. SKILL.md encodes the full local commit flow (inspect → branch-check → stage → compose → commit → verify → optional amend/fixup) and the four guardrails as never-do/always-do rules with exact commands. The reference holds the conventional-commit type/scope cheat-sheet and copy-paste message templates.

**Why:** This is the cross-link target for `git-operations`, so it must exist and be stable first.

**Files:**

- Create: `skills/git-commit/SKILL.md`
- Create: `skills/git-commit/references/commit-types.md`

**Interfaces:**

- Consumes: None
- Produces: skill `name: git-commit` and its trigger phrasing — Task 3 links to it by name; Task 2 reads `name`/`description` into the manifests.

**Sketch:**

SKILL.md structure (headings the body must contain):

```markdown
---
name: git-commit
description: Use when staging changes and creating a git commit — deriving a conventional-commit message from the diff and running the commit safely (review before staging, no blind `git add .`, multiline bodies via -F, branch check first).
---

# git-commit

## When to use
## Flow (inspect → branch-check → stage → compose → commit → verify)
## Guardrails
  ### 1. Never blind-stage        (ban `git add .`/`-A`; status+diff review → explicit pathspecs)
  ### 2. Never chain -m for bodies (use `git commit -F <file>` or heredoc)
  ### 3. Never inject trailers      (no Co-Authored-By / tool attribution unless asked)
  ### 4. Check the branch first     (on main/default → offer `git switch -c <new>` before committing)
## Splitting a mixed tree into logical commits
## Interaction model (derive-then-confirm; ask when diff spans unrelated concerns)
## ⚙ Adjust these   (rtk prefix, `-s` signoff defaults — how to swap out)
```

Canonical multiline-body pattern the skill prescribes (guardrail 2):

```bash
# write body to a temp file, commit with -F, then remove it
git commit -s -F "$msgfile"   # NOT: git commit -m a -m b -m c
```

**Gotchas:**

- `description` must start with "Use when…", stay ≤ 500 chars, frontmatter ≤ 1024 chars total.
- Guardrail commands are generic; the `-s` signoff and `rtk` prefix appear only inside the "⚙ Adjust these" callout, not baked into every example.
- Do not prescribe `Co-Authored-By` anywhere — guardrail 3 forbids it.
- No push/PR content — scope stops after verify + optional amend/fixup (amend only on unpushed local commits).
- Branch creation in guardrail 4 uses `git switch -c <new>`, never `git checkout -b` (see Global Constraints — modern porcelain).
- Keep the derive-then-confirm model explicit: present the proposed message for confirmation before committing.

**Dependencies:** None

## Task 3: Author `git-operations` content

**What:** Write `skills/git-operations/SKILL.md` (the decision router), `references/decision-map.md` (the full situation→operation routing table), and `references/recovery.md` (the reflog/undo cookbook). The router covers everyday + recovery operations only; each operation card carries when-to-choose-it-over-alternatives, the safe command sequence, and an undo path. The Committing fork is a one-line cross-link into `git-commit`.

**Why:** This is the judgment layer over raw git — the second and final skill of the pair.

**Files:**

- Create: `skills/git-operations/SKILL.md`
- Create: `skills/git-operations/references/decision-map.md`
- Create: `skills/git-operations/references/recovery.md`

**Interfaces:**

- Consumes: `git-commit` skill name from Task 1 (Committing fork links to it).
- Produces: skill `name: git-operations` and its trigger phrasing — Task 4 reads `name`/`description` into the manifests.

**Sketch:**

Decision forks the router must resolve (the spine of SKILL.md + decision-map.md):

```markdown
| Situation                | Choose → (not →)                                   | Undo path         |
|--------------------------|----------------------------------------------------|-------------------|
| Undo a commit            | reset --soft (local) / revert (shared) / reflog    | reflog restore    |
| Discard changes          | restore (tracked) / restore --staged / clean (new) | (destructive—warn)|
| Park work-in-progress    | stash  vs  `git switch -c <new>`                   | stash pop / switch back |
| Integrate upstream       | merge  vs  pull --rebase (light)                   | reset --merge / ORIG_HEAD |
| Publish                  | push (wrong-branch + no-force-to-shared checks)    | —                 |
| Committing               | → see git-commit skill                             | —                 |
| "I broke something"      | → references/recovery.md (reflog cookbook)         | —                 |
```

**Gotchas:**

- Scope is everyday + recovery ONLY. Add a visible "Out of scope → future sibling skill" note listing: interactive rebase, amend/fixup/autosquash, cherry-pick, force-push, submodules, worktrees, bisect.
- Every operation card must carry an undo path — that is what makes the router "safe".
- Discard fork must never recommend a blind `git checkout .`; route to `restore` / `restore --staged` / `clean` and warn on destructive ones.
- Modern porcelain everywhere (see Global Constraints): branch moves/creation use `git switch` / `git switch -c`, file discard/unstage uses `git restore` / `git restore --staged`. `checkout` appears only where nothing modern covers it, flagged as such. Audit every card for this before finishing.
- Committing fork is a one-line cross-link only — do not duplicate git-commit's guardrails here.
- Same "⚙ Adjust these" callout convention (rtk prefix / signoff) as git-commit; commands otherwise generic.
- `description` starts with "Use when…", ≤ 500 chars, frontmatter ≤ 1024 chars.

**Dependencies:** Task 1 (needs the `git-commit` name to link to)
