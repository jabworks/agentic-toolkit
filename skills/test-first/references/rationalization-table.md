# TDD Rationalization Table

Common reasons agents (and developers) use to skip writing tests — and why they're wrong.

| Rationalization                                        | Reality                                                                                                                                      | Counter                                                                                         |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| "This change is too small to need a test"              | Small changes break things too. The test takes 2 minutes.                                                                                    | Write the test. It documents the behavior even if it never catches a regression.                |
| "I'll write tests after the implementation is working" | Tests written after are biased by the implementation you built. You test what you know works, not what could break.                          | Tests first force you to think about edge cases before you're anchored to an implementation.    |
| "The existing tests cover this"                        | They cover the old behavior. The new behavior needs its own test.                                                                            | Add a test for the new behavior. Don't assume coverage.                                         |
| "This is just UI, tests don't apply"                   | Logic in UI components (conditional rendering, state transitions, handlers) can and should be tested. Layout doesn't need tests. Logic does. | Separate the logic from the layout. Test the logic.                                             |
| "We're moving fast, we'll add tests later"             | "Later" doesn't come. The feature ships, the next feature starts, the tests never get written.                                               | Tests now are cheaper than debugging later. The test is part of the task, not optional cleanup. |
| "The type system already catches this"                 | Types catch shape errors. Tests catch behavioral errors. These are different things.                                                         | Types and tests are complementary, not substitutes.                                             |
| "Running tests takes too long"                         | Running the specific test for the specific change takes seconds.                                                                             | Run only the relevant test file, not the full suite.                                            |
| "I need to update the spec to make the test pass"      | If you're rewriting the spec to match new output, you're not fixing a bug — you're hiding one.                                               | Stop. Explain what changed and why. Get explicit approval before touching existing specs.       |
| "This is a prototype, no tests needed"                 | Prototypes become production code. Untested prototypes become untested production code.                                                      | Decide: is this throwaway? If yes, delete it. If it might ship, test the core logic.            |
| "The test is too hard to write"                        | If the test is hard to write, the code is too coupled or too complex.                                                                        | Hard-to-test code is a design smell. Simplify the code, then write the test.                    |
